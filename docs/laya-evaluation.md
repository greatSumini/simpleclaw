# Laya 도입 검토 — SimpleClaw 적합성 심층 분석

- 대상: https://github.com/NandhaKishorM/laya (Convai Innovations, Apache 2.0)
- 작성일: 2026-09-20
- 결론 한 줄: **전면 도입 반대. 단 하나의 유스케이스(메일 `ignore` 사전 컷)만 조건부 가치 있음. 코드 변경 0인 섀도우 평가부터.**

---

## 1. Laya가 무엇인가

비자기회귀(non-autoregressive) **타입드 결정 엔진**. 텍스트를 생성하지 않고, 한 번의 forward pass로 구조화된 판정만 뱉는다.

| 체크포인트 | 인코더 | 파라미터 | 컨텍스트 | 용도 |
|---|---|---|---|---|
| `laya` | ModernBERT-large | 421M | 512 | 영어 전용 |
| `laya-multilingual` | mmBERT-base | 322M | 1024 | 100+ 언어 |
| `laya-typed-decisions` | ModernBERT-large | 421M | 1024 | 결정 워크플로 파인튜닝본 |

**결정 프리미티브 3종**
- `choice` — 카테고리 분류 + 옵션별 확률
- `score` — 순서형 척도 (예: 긴급도 0~2)
- `noul` — 이진 확률 (0.0~1.0), proper scoring rule로 캘리브레이션 학습

**성능**: T4 GPU 32.8ms/질문, 배치 10개 시 7.2ms/질문. CPU 193~464ms.
**품질**: typed-decisions 0.766 (경쟁 Jev 0.727), 지연 7.8배 빠름, ECE 3배 우수.

## 3. 지점별 적합도 판정

### 3-1. 메일 중요도 분류 — **적합도 상 (유일한 진짜 후보)**

laya의 `triage_questions()` 프리셋이 정확히 이 도메인(intent / urgency / frustration / churn)이다. 질문 스키마도 자연스럽게 떨어진다:

```python
{
  "verdict":       {"type": "choice", "criteria": {"important": "...", "ambiguous": "...", "ignore": "..."}},
  "needs_reply":   {"type": "noul",   "instructions": "사람의 답장·결정·조치가 필요한가?"},
  "urgency":       {"type": "score",  "criteria": ["급하지 않음", "며칠 내", "즉시"]},
}
```

**결정적 제약**: 현재 classifier는 `oneLineSummary`·`suggestedActions`·`contextNotes`를 **생성**한다. laya는 생성을 못 한다. 따라서 1:1 교체가 불가능하고, **캐스케이드만 가능**:

```
메일 → 도메인 패턴 필터 (현행, 0ms)
     → laya (~0.3s, 로컬)
        ├─ ignore 이고 conf ≥ θ  → 즉시 컷. Claude 호출 없음
        └─ 그 외                  → 현행 Claude 분류기 (요약·제안 생성)
```

**기대효과**: ignore가 81.5%. 그중 고신뢰 부분만 컷해도 LLM 호출 일 21.8 → 6~8건. 월 $120 내외 절감 + 메일 알림 지연이 수 초 → 0.3초.

**학습 데이터가 이미 있다**: `events`에 `importance.classify` 3,873건(mode/verdict/제목/발신자 meta 포함). 게다가 `mail.resolved` 256건은 사람이 실제로 반응한 기록 = 골드 라벨. `sender_policies` 테이블도 사람이 직접 만든 라벨이다. 파인튜닝 데이터셋 구축 비용이 거의 0에 가깝다 — 이 점이 이 후보를 살리는 가장 큰 요인.

### 3-2. skill-detector — **적합도 중, 그러나 지금은 불가**

형태상으로는 완벽한 `choice` 태스크(현재 14개 옵션, laya의 high-cardinality 한계 20개 아직 미도달). 이득도 명확하다 — Discord 메시지마다 Claude Code CLI 서브프로세스를 띄워 최대 20초를 블로킹하는 구조라, 로컬 추론으로 바꾸면 **체감 응답 지연이 매 메시지 2~5초 줄어든다.** 비용보다 이쪽이 크다.

**그런데 막힌다**: laya는 zero-shot이 typed-decisions에서 사실상 랜덤이다(0.36 vs 랜덤 0.318). README가 직접 "most value comes from fine-tuning"이라 명시한다. skill description은 완전히 학습 분포 밖이므로 파인튜닝이 필수인데 — **라벨 데이터가 없다.** 확인 결과 skill 선택 이력이 `events`에 전혀 기록되지 않고(`type like '%skill%'` → 0건), `sessions.last_skill`에 스레드별 최신값만 덮어쓰기로 남는다.

**선행 조치**: skill 감지 결과를 `events`에 `type='skill.detect'`로 로깅하는 것부터. 이건 laya와 무관하게 그 자체로 가치 있다(어떤 skill이 실제로 쓰이는지 관측 불가 상태). 2~3개월 축적 후 재검토.

### 3-3. 프롬프트 인젝션 가드 — **신규 가치, 보조 신호로만**

laya에 `guard_questions()` 프리셋이 있다. SimpleClaw는 Discord에서 임의 텍스트를 받아 **bypass permissions 모드의 Claude Code를 실행**하는 구조라 표면이 넓다. 외부 repo 채널 메시지에 대한 사전 스크리닝은 방어적으로 의미 있다.

단 held-out 정확도 0.698. **차단 결정에 쓰면 안 되고**, 고신뢰 히트를 이벤트로 기록해 사후 관측하는 용도까지. 기존 `session-boundary-guard` skill과 역할이 겹치지 않고 보완적이다.

### 3-4. 이슈 복잡도 / 도메인 프리필터 — **부적합**

- 이슈 복잡도: 전체 기간 5건. ROI 없음.
- `SKIP_DOMAINS` 하드코딩 리스트: 현재 0ms에 100% 정확. 확률 모델로 바꾸면 순수 퇴보.

## 4. 아키텍처 리스크 (도입 결정을 실제로 좌우하는 부분)

### 4-1. 런타임 임피던스 미스매치 — 가장 큰 비용

laya는 **Python 패키지**(`pip install laya`). SimpleClaw는 Node 단일 프로세스 + launchd(`com.simpleclaw`) 단일 서비스. 도입하면:

- Python 사이드카(FastAPI 등) + **두 번째 launchd 서비스** 필요
- 헬스체크·재시작·버전 고정·가상환경 관리가 새로 생김
- 모델 상주 메모리 1.5GB/체크포인트. 라우터 preload면 3~4.5GB 상주
- `Router(preload=True)` 아니면 언어 전환 시 **7~10초** 재로딩 — 한/영 혼재 메일함에서 치명적이므로 preload 필수 → 메모리 하한이 고정됨

현재 SimpleClaw의 운영 단순성(launchctl kickstart 한 줄로 전체 재시작)이 여기서 깨진다. **이게 월 $120 절감과 맞바꿀 만한가가 핵심 질문이다.**

### 4-2. 하드웨어 — 벤치마크가 이 환경에 없다

모든 수치가 **Tesla T4 GPU 기준**. 이 머신은 macOS/Apple Silicon, CUDA 없음. CPU 폴백은 193~464ms로 명시되어 있고, MPS 백엔드 성능은 **README에 데이터가 없다**. 실측 전에는 미지수.

다만 비교 대상이 Claude Code CLI 서브프로세스 spawn(수 초 단위)이므로, CPU 464ms라도 여전히 한 자릿수 배 빠르다. 지연시간 논거는 하드웨어와 무관하게 성립한다.

### 4-3. 사이드카를 피하는 대안 경로 (검증 가치 높음)

`package.json`에 **`@huggingface/transformers` ^4.2.0이 이미 있다.** 그런데 `src/` 어디에서도 쓰이지 않는다(유령 의존성 — 과거 시도의 흔적으로 보임). 즉 **Node 프로세스 내 로컬 추론 경로가 이미 열려 있다.**

ModernBERT/mmBERT 백본은 ONNX 변환이 가능하다. 문제는 laya의 질문 스키마 헤드가 커스텀이라 변환 난이도가 미지수라는 점. **변환이 되면 사이드카·두 번째 서비스·Python 환경이 전부 사라진다.** 4-1의 비용 대부분이 소거되므로, 이 검증이 Phase 0에서 가장 우선순위가 높다.

### 4-4. 한국어 — 최대 품질 불확실성

SimpleClaw 메일은 한국어 우세 + 영어 혼재. laya 수치:

| | `laya` (영어) | `laya-multilingual` |
|---|---|---|
| MASSIVE intent (영어) | 0.783 | 0.657 |
| MASSIVE (13개 비영어) | 0.306 | **0.451** |
| XNLI (14개 비영어) | 0.521 | **0.731** |

즉 한국어 경로는 `laya-multilingual`인데 intent 분류가 0.451. 한국어 단독 수치는 공개되어 있지 않다. 그리고 영어 체크포인트는 비영어에서 "**95.2% 확신으로 정확도 0**"(크메르 문자)을 기록한다 — 조용한 고신뢰 오답이 실재한다는 뜻이고, 이건 confidence 게이팅 설계 전체를 위협한다.

### 4-5. 과신 (over-confidence)

README가 자인한다: 두 체크포인트 모두 over-confident 상태로 출하되며 ECE 0.466(영어)/0.314(다국어). temperature scaling 재적합 후에야 0.081/0.106. **캘리브레이션 없이 `conf >= 0.9` 같은 게이팅을 걸면 설계가 성립하지 않는다.** 그리고 캘리브레이션은 (질문 타입 × 옵션 수)별로 재적합해야 하고, 데이터 분포가 드리프트하면 재적합이 필요한 **지속 유지보수 항목**이다.

### 4-6. 프로젝트 성숙도

Convai Innovations 단일 조직 산출물, 공개 시점이 최근. Apache 2.0에 가중치 공개는 긍정적이지만, 장기 유지보수·보안 패치 보장은 없다. 의존하려면 **모델 가중치를 자체 미러링**하고 특정 리비전에 핀 고정하는 전제가 필요하다.

## 6. 지배적 리스크: false negative

모든 리스크 중 하나가 나머지를 압도한다 — **중요한 메일을 `ignore`로 컷하는 것.** 이건 조용히 실패하고, 되돌릴 수 없으며, 발생 사실조차 관측되지 않는다. 절감액은 선형이지만 이 손실은 그렇지 않다.

따라서 설계 제약을 **불변식으로 못 박는다**:

1. laya는 **`ignore` 방향으로만** 단독 결정할 수 있다.
2. `important` / `ambiguous` 판정은 **절대** laya 단독으로 확정하지 않는다 — 반드시 Claude 분류기로 넘긴다.
3. 임계값 θ는 캘리브레이션 후 **ignore recall ≥ 0.98**을 만족하는 값으로만 설정한다.
4. laya가 컷한 메일도 `events`에 전량 기록해 **사후 감사 가능**해야 한다.
5. 롤백은 환경변수 한 개(`LAYA_ENABLED=0`)로 즉시 가능해야 한다.

## 7. 검증 전략 — 각 단계에 중단 기준 포함

### Phase 0 — 환경 실현성 (반나절, 코드 변경 0)
- `pip install laya` → Apple Silicon에서 동작 확인
- MPS / CPU 지연 실측 (배치 1, 5, 10)
- **ONNX 변환 가능성 조사** — 되면 4-1 비용 대부분 소거 (최우선)
- 실 메일 20건 수동 투입, 한국어 sanity check

> **중단 기준**: 한국어 20건에서 ignore 판별이 눈에 띄게 무작위면 여기서 종료. 이 단계는 반나절이므로 위험 없이 시도 가능.

### Phase 1 — 오프라인 섀도우 평가 (1일, 코드 변경 0)
- `events`에서 `importance.classify` 과거 판정 1,000건 덤프
- laya zero-shot vs 기존 Claude 판정 혼동행렬
- 언어별(한/영) 분리 집계 — 합산 수치는 한국어 취약을 가린다
- `mail.resolved` 256건을 골드 라벨로 별도 측정

> **중단 기준**: zero-shot ignore recall < 0.95 → Phase 2로 진행할지를 재검토 (README상 zero-shot은 원래 약하므로, 여기서 탈락해도 파인튜닝 후 재도전 가치는 남음)

### Phase 2 — 파인튜닝 (2~3일)
- 3,873건 + `sender_policies` + `mail.resolved`로 데이터셋 구축
- RLCD 파인튜닝 (Kaggle 노트북 절차, 2×T4 4~5h)
- **temperature 캘리브레이션 재적합 필수**, ECE 측정
- 시계열 split (과거 학습 / 최근 2주 테스트) — 랜덤 split은 낙관 편향

> **중단 기준**: ignore recall < 0.98 또는 precision < 0.90 → **여기서 종료.** 가장 중요한 게이트.

### Phase 3 — 온라인 섀도우 (2주, 실제 결정에는 미반영)
- 프로덕션에서 laya를 병행 실행, 판정만 `events`에 기록
- 실제 결정은 100% 기존 Claude 분류기
- 2주 후 불일치 케이스 전수 리뷰
- 지연·메모리·크래시 등 운영 지표 동시 수집

> **중단 기준**: 놓쳤을 important가 1건이라도 나오면 θ 상향 또는 종료

### Phase 4 — 제한적 활성화
- 고신뢰 `ignore`만 컷, `LAYA_ENABLED` 플래그로 즉시 롤백 가능
- 주간 감사 리포트(컷된 메일 목록)를 daily-digest에 포함
- 1개월 후 실측 절감액·사고 0건 확인 시 θ 완화 검토

## 8. 더 싼 대안 — 먼저 비교되어야 함

laya 도입 전에 반드시 비교해야 할 것:

**(a) `@huggingface/transformers` + 소형 다국어 임베딩 + 로지스틱 회귀**
이미 의존성에 있다. 발신자/제목/본문 임베딩 + 3,873건 라벨로 경량 분류기. Python 사이드카 없음, Node 내 완결, 모델 100MB급. laya 효과의 상당 부분을 운영 복잡도 증가 없이 얻을 가능성이 높다.

**(b) 발신자 통계 기반 베이지안 사전확률**
`sender_policies` + 과거 판정 이력으로 발신자별 ignore 사전확률. ML 없음. 반복 발신자가 많은 메일함에서는 이것만으로 호출의 상당수가 컷될 수 있다. **구현 비용 가장 낮음 — 이걸 먼저 재봐야 한다.**

**(c) 분류기 모델을 Haiku로 다운그레이드**
`classifyMail`이 현재 모델 미지정 = CLI 기본 모델(고가)을 쓴다. `skill-detector`처럼 `model: 'claude-haiku-4-5-20251001'` 한 줄만 넣으면 **오늘 당장, 1줄 변경으로** 메일 분류 비용이 한 자릿수 배 떨어진다. 절감액만 목표라면 laya의 ROI 대부분이 이 한 줄로 선점된다.

> **(c)는 laya 검토와 무관하게 즉시 시행 검토 가치가 있다.** 다만 ignore 판별 품질 저하 여부는 Phase 1과 동일한 섀도우 평가로 확인해야 한다.

## 9. 최종 권고

| | 판정 |
|---|---|
| 전면 도입 | **반대** |
| 메일 `ignore` 사전 컷 | **조건부 찬성** — Phase 0~2 통과 시에만 |
| skill-detector 대체 | **보류** — 라벨 데이터 없음. 로깅부터 |
| injection 가드 | **관측 용도로만 검토 가치** |
| router / memo 대체 | **명시적 반대** — 결정론 코드의 퇴보 |

**즉시 할 것 (laya와 무관하게 가치 있음)**
1. `skill.detect` 이벤트 로깅 추가 — 현재 skill 사용 실태가 관측 불가
2. `classifyMail`의 모델을 Haiku로 낮추는 안 검토 (1줄, 큰 절감)
3. 발신자별 ignore 사전확률 컷 (대안 b) 타당성 검토

**laya에 대해 할 것**
Phase 0만 먼저 (반나절, 코드 변경 0). 특히 **ONNX 변환 가능성** — 이게 되면 Python 사이드카라는 최대 비용이 사라져 손익이 뒤집힌다. 안 되면 laya 도입은 월 $120을 위해 운영 표면을 2배로 늘리는 거래가 되고, 그 거래는 권하지 않는다.
